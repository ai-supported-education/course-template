# Руководство автора курса

## Сначала спроектируйте маршрут, потом пишите карточки

Заполните в `curriculum/course.json` аудиторию, входные знания, modules и capstone.
У каждой сессии должны быть один наблюдаемый результат, ясный `DONE` и оценка
30–60 минут. Порядок сессий — зависимость по умолчанию: учащийся видит только
ближайший доступный шаг.

Не превращайте module в двухчасовой «базовый блок». Если для понимания нужны две
идеи, две ошибки или два независимых зелёных результата — это две карточки.

## Контракт одной карточки

README должен дать достаточный контекст, чтобы учащийся мог объяснить решение, а не
только угадать API:

1. Измеримый outcome и ограниченный scope.
2. Причинную ментальную модель, а не перечень методов.
3. Как минимум два маленьких примера кода или явно расписанных сценария, если тема
   относится к коду.
4. Timeline, data flow или таблицу там, где важен порядок действий.
5. Границу аналогии с уже знакомым стеком — только для переходного курса.
6. Минимум два правдоподобных ошибочных решения и причину ошибки.
7. Точное задание, ограничения, отдельно описанные local check и agent review.
8. Проверяемый список DONE.

Текст для внимательного чтения должен укладываться примерно в 10–15 минут. Если
объяснение длиннее, это сигнал разделить тему или вынести справочный материал.

## Упражнение и проверка

Выбирайте форму по учебной цели:

- **quiz / observe** — предсказать конкретное поведение по коду и сценариям;
- **debug** — найти одну целевую причину регрессии;
- **complete / build** — дописать небольшую функцию или компонент;
- **refactor** — заменить неверную модель на более ясную без расширения scope;
- **integrate / ship** — собрать несколько уже освоенных частей в целый результат.

Starter должен быть в рабочем состоянии, но содержать ровно одну целевую проблему.
Acceptance test обязан падать на starter по ожидаемой причине и становиться зелёным
после минимального корректного решения. Проверяйте поведение, видимое пользователю
или публичному контракту, а не имя hook, файла или внутренний алгоритм.

В quiz рядом с вопросом всегда показывайте исполнимый или мысленно исполнимый код и
порядок действий. Не говорите учащемуся, что писать в свободном `reason`: агент
проверит собственное объяснение отдельно.

## Checks, review и подсказки

`pnpm session:check` — локальная автоматизация. Он не запускает Codex. В manifest
помещайте только checks, для которых есть реализация в registry runner.

`review` означает отдельный смысловой шаг: после зелёного check агент читает пакет
`pnpm session:review`, возвращает `PASS` или `NEEDS_WORK`, затем записывает verdict.
Не маскируйте архитектурную оценку хрупким поиском строк в исходниках.

Для каждой практической карточки подготовьте три уровня в `course-support`:

1. напоминание концепции;
2. указание области, где искать проблему;
3. структура исправления или маленький reference fragment.

Main branch не должна содержать ключи quiz, готовые решения или открытые файлы
подсказок. Создайте ref `course-support` от основной ветки и храните эти файлы
только там.

GitHub не переносит дополнительные Git refs при создании repository из template.
Поэтому сразу после создания нового курса выполните:

    git switch -c course-support
    git push -u origin course-support
    git switch -

Затем добавляйте support-файлы, переключившись в эту ветку. Перед проверкой hint в
обычном clone достаточно выполнить `git fetch origin`; в personal fork —
`git fetch upstream`.

## Рабочий цикл автора

1. Замените демонстрационный module и первую карточку реальной темой.
2. Запустите `pnpm install` и `pnpm session:validate`.
3. Пройдите карточку из чистой копии как учащийся.
4. Убедитесь, что starter воспроизводит цель, а минимальное решение делает checks
   зелёными.
5. Выполните review по rubric и только затем публикуйте карточку.
6. Попросите пилотного учащегося пройти сессию; непонятное место исправляйте в
   объяснении, примере или границе задания, а не только в ключе quiz.

React- и FSD-специфичные решения описаны отдельно в
[React profile](stack-profiles/react.md); не переносите их в общий стандарт.
