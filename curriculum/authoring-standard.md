# Стандарт учебного материала

Сессия считается реализованной не по наличию README, а когда учащийся может за
30–60 минут получить заявленный результат, оставить проверяемый evidence и
закончить в безопасном состоянии. Этот документ — общий контракт. Дополнительные
правила подключаются через `profiles` в `course.json`.

## Обязательная структура карточки

Каждый learner-facing README содержит:

1. Измеримый результат и явно ограниченный scope.
2. Входное состояние: знания, файлы, инструменты, данные и права доступа.
3. Причинную модель, а не только последовательность команд или формул.
4. Не меньше двух небольших разобранных примеров или конкретных сценариев.
5. Timeline, data flow, схема или таблица, если порядок или связи нельзя ясно
   передать коротким текстом.
6. Разбор минимум двух правдоподобных ложных решений и причины их ошибки.
7. Точное задание, ограничения и ожидаемые артефакты.
8. Раздельное описание local check, эмпирической проверки и agent review — только
   тех способов, которые действительно используются.
9. Проверяемый список DONE, включая cleanup/rollback для практики с внешним
   состоянием.
10. Следующий шаг без требования начать его в текущей сессии.

Теория должна занимать примерно 10–15 минут внимательного чтения. Более длинную
тему делите на несколько завершённых сессий.

## Epistemic integrity

Материал явно различает пять типов утверждений:

- **source fact** — подтверждено указанным первичным или авторитетным источником;
- **assumption** — принято для задачи и ограничивает применимость вывода;
- **expected** — прогноз до запуска, расчёта или наблюдения;
- **observed** — действительно получено учащимся и сохранено в evidence;
- **inference** — вывод из фактов, допущений и наблюдений.

Нельзя придумывать измерения, логи, цитаты, успешные запуски или состояния внешней
системы. Пример данных помечается как synthetic/sample. Для изменчивых фактов
указываются источник и дата проверки; ключевые внешние источники должны быть
доступны без авторского контекста.

## Карта понятий и profiles

У каждой сессии в `course.json` обязательны `requires`, `introduces` и `defers`:
что уже известно, что полноценно вводится сейчас и что только названо, но
объясняется позже. Concept ids устойчивы и машиночитаемы. Validation отклоняет
неизвестные prerequisites, повторные introductions и deferred concepts без
будущего introduction.

Корневой `profiles` — список применяемых контрактов. Общие профили находятся в
`docs/course-profiles/<id>.md`, стековые — в `docs/stack-profiles/<id>.md`.
Профили компонуются: например, переходный Java-курс может выбрать `transition` и
`software`, а сетевой практикум — `lab`, `quantitative` и `network-safety`.

## Evidence contract

Каждая сессия объявляет, что останется после работы и как это проверяется:

```json
"checks": ["review"],
"evidence": {
  "produces": ["measurements.csv", "Короткий вывод в observations.md"],
  "verifiedBy": ["empirical", "agent"]
}
```

Допустимые verification modes:

| Mode | Что означает |
| --- | --- |
| `automated` | Реализованный check воспроизводимо проверяет artifact или поведение |
| `empirical` | Результат получен наблюдением или измерением по описанной процедуре |
| `agent` | Агент сверяет смысл, rubric и достаточность evidence |
| `manual-approval` | Нужна явно названная проверка человеком с подходящей ролью |

`done` задаёт обязательные критерии, а `evidence` называет материал, по которому
можно доказать их выполнение. `review` всегда отражается как `agent`; любой
не-`review` check — как `automated`. Эмпирическую или ручную проверку обычно
сочетайте с `review`, чтобы runner мог зафиксировать решение по rubric.

## Выбор формы практики

- `observe` / `quiz` — предсказать и объяснить конкретный сценарий;
- `derive` / `calculate` — получить вывод с промежуточными шагами и проверкой
  размерности, границ или контрпримером;
- `measure` / `experiment` — выполнить воспроизводимую процедуру и сохранить сырые
  наблюдения отдельно от интерпретации;
- `configure` / `diagnose` — получить baseline, внести ограниченное изменение или
  локализовать причину, затем доказать состояние системы;
- `design` — создать решение в ограничениях и защитить trade-offs;
- `complete` / `debug` / `build` / `refactor` / `integrate` / `ship` — изменить
  программное поведение и подтвердить публичный контракт.

Используйте ближайший шаблон из `templates/sessions/`, а не притворяйтесь, что
каждая дисциплина является code exercise.

## Кодовая практика

Этот раздел применяется только к карточкам с исполняемым starter:

- starter содержит одну целевую проблему;
- acceptance test падает на starter по описанной причине;
- минимальное корректное решение делает test зелёным;
- test проверяет наблюдаемое поведение, а не имя API или устройство реализации;
- архитектурные ограничения, которые нельзя устойчиво проверить автоматически,
  остаются в rubric и agent review.

Базовый runner реализует `quiz`, `review` и TypeScript/Vitest-варианты
`typecheck`, `unit`, `integration`. Для другого языка замените реализацию registry
и докажите её на starter и минимальном решении; одного нового label в manifest
недостаточно.

## Лабораторная и внешняя практика

Карточка, меняющая внешнее состояние или взаимодействующая с сетью, радиоэфиром,
оборудованием либо облачным сервисом, обязана содержать:

- разрешённый target и границы воздействия;
- preflight состояния, инструментов, прав и канала восстановления;
- baseline до изменения;
- stop conditions для неожиданных результатов или потери управления;
- минимальное обратимое действие;
- способ сохранить сырые evidence и параметры среды;
- политика повторного запуска без тихого перезаписывания raw evidence и видимый
  порядок `expected → action start → observed`;
- cleanup/rollback и проверку конечного состояния.

По умолчанию используйте simulation, localhost, synthetic data и passive
observation. Активное сканирование, передача в эфир и изменение не принадлежащих
учащемуся систем не подразумеваются учебным заданием.

## Rubric

Rubric разделяет:

1. **invariants** — обязательные наблюдаемые критерии для PASS;
2. **valid alternatives** — допустимые способы получить тот же результат;
3. **optional improvements** — идеи, которые не блокируют PASS;
4. **evidence and safety** — достаточность доказательств и соблюдение границ.

Не делайте скрытый «идеальный авторский путь» единственным правильным решением.

## Quiz, подсказки и ответы

- `quiz.json` хранит только машиночитаемые ids, варианты и настройки проверки.
- `quiz.md` содержит самодостаточный код или полный сценарий, исходные значения,
  порядок действий и вопрос.
- Свободный `reason` учащийся пишет своими словами; prompt не подсказывает формулу
  правильного объяснения.
- Hints, quiz keys и reference solutions находятся только в Git ref
  `course-support`.
- `session:hint` раскрывает один следующий уровень: концепция → область поиска →
  структура исправления. Runner не применяет solution автоматически.

Это защита от случайного раскрытия в IDE, а не криптографическая защита от
владельца repository.

## Проверка и независимый content-review

`pnpm session:check` запускает локальную автоматизацию, а не Codex. Agent review
проверяет смысл, rubric, корректность inference, достаточность evidence и отсутствие
обхода цели. Сессия с `review` не завершается без актуального записанного `PASS`.

Каждая новая или существенно изменённая карточка затем проходит author-side review
fresh subagent без истории генерации. Он сначала читает learner-facing packet,
потом сверяет profile contracts, concept graph, rubric, checks, evidence и соседние
карточки. `PASS` допустим без BLOCKER и MAJOR; любое исправление устаревает по hash
и требует нового reviewer. После session PASS всех карточек нужен module PASS.

Полный протокол: [content-review-protocol.md](content-review-protocol.md).
